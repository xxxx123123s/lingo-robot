## 两个用法

### 1. 直通回放：说 → 耳机立刻听到自己（延迟约 128ms）

```bash
ssh pi@192.168.137.160
cd ~ && ./echo.sh
```

调延迟（越低越"跟嘴"，但可能爆音）：

```bash
PERIOD=256 BUF=1024 ./echo.sh   # 约 64ms
PERIOD=1024 BUF=4096 ./echo.sh  # 平稳模式，约 256ms
```

### 2. 语音闭环：说 → 实时识别 → 耳机念回来　（主力脚本）

```bash
cd ~ && python3 talk.py          # VAD 检测到人声才识别，停顿 0.5 秒断句
python3 talk.py -q               # 只识别不出声
python3 talk.py -v cmn+m3 -s 190 # 男声 / 语速 190
python3 talk.py -f x.wav         # 用 16k wav 测试，不占麦克风
python3 talk.py --no-vad         # 关掉 VAD，退回端点检测模式
```

VAD（silero）的作用：只在检测到人声时才把音频送进识别器。
不加 VAD 时，环境噪声会被模型"脑补"成文字（实测出现过
`这不一样我也见过一下那我再见过一些见过我还要借我借过一会儿我` 这种幻觉）。

另外两个精度调整：

- **预滚 0.35 秒**：VAD 触发前的那段音频会一起送进识别器，避免吞掉第一个字
  （实测「你好」的「你」就是这样补回来的）。
  注意：预滚解决不了「今天→天」这类漏字，那种是模型本身的能力问题
  （把开头 0/0.2/0.35 秒分别切掉，识别结果完全一样）。
- **热词**：`~/hotwords.txt` 里的词会被加权，格式是**每个汉字用空格隔开**：

  ```
  许 鑫
  树 莓 派
  ```

  启用热词会切到 `modified_beam_search` 解码（总耗时从约 1.1 秒升到约 1.9 秒/句，
  仍远快于实时）。不想要就加 `--no-hotwords`。

- **最短语音过滤**：一段音频里真正有声的时长不足 0.3 秒就直接丢弃，避免咳嗽、碰麦
  之类的短促音被当成话送进识别器（否则会打印「有声音但没识别出内容」）。

- **录音复盘**：`python3 talk.py --save-dir ~/segs` 会把每句存成 wav，
  用 `python3 seginfo.py ~/segs/xxxxxx.wav` 可以打印能量包络并对比不同切法的识别结果。

### 3. 真对话：说 → 识别 → DeepSeek → 语音回答

先填密钥到 `/home/pi/llm.json`（文件权限已设 600）：

```json
{
  "api_key": "sk-你的密钥",
  "base_url": "https://api.deepseek.com",
  "model": "deepseek-chat"
}
```

然后：

```bash
cd ~ && python3 chat.py              # 开始对话，带上下文记忆（保留最近 6 轮）
python3 chat.py --say "你好"         # 只测 LLM + TTS，不占麦克风
python3 chat.py --quiet              # 只打印不朗读
python3 chat.py -v cmn+m3 -s 180     # 换音色
```

人设写在 `llm.json` 的 `system` 字段，默认是「小派」桌宠，回复限制 40 字以内
（长了念起来很折磨）。改人设直接编辑这个字段即可，不用改代码。

## 语音合成（TTS）方案

espeak-ng 的中文是**一字一顿的机械音**，救不回来，所以换成三级方案：

| 引擎 | 说明 | 实测 |
|---|---|---|
| **sapi**（默认） | 走 PC 上的 Windows SAPI 中文音色，局域网取 WAV | 合成一句 **0.17s**，音质自然 |
| edge | 微软神经网络语音，音色最好 | 国内网络成功率仅 **2~5/10**，不可靠 |
| espeak | 树莓派本机离线兜底 | 机械音，仅应急 |

**关键前提：PC 上的语音服务要开着。**

```bash
# PC 上双击运行（或加到开机启动）
D:\智能桌宠\麦克佛加喇叭\pc\启动语音服务.bat
```

服务监听 `192.168.137.1:8765`，树莓派 `GET /tts?text=你好&voice=huihui&rate=180` 取 WAV。

音色可选 `huihui`（女，默认）/ `kangkang`（男）/ `yaoyao`（女）。

```bash
python3 chat.py -v kangkang --rate 200   # 男声、语速快一点
python3 chat.py --tts edge               # 试试在线音色（可能失败）
python3 talk.py -f x.wav -v yaoyao       # 复读脚本也能换音色
```

> 为什么不用本地神经网络 TTS？实测 sherpa-onnx 的 VITS 中文模型在这台
> 32 位树莓派上 **RTF 高达 17~23**（1 秒语音要合成 20 秒），完全不可用。


## 为什么换了识别引擎

实测同一台机器、同一段音频：

| 引擎 | 模型 | 解码耗时(5.8s 音频) | RTF | 首字延迟 |
|---|---|---|---|---|
| Vosk | vosk-model-small-cn-0.22 | 11.5s | **1.98** | 无法实时 |
| sherpa-onnx | streaming-zipformer-zh-14M int8 | **1.0s** | **0.18** | **0.1s** |

Vosk RTF≈2 意味着解码永远追不上说话速度，必然丢帧、断句稀碎。
根因是系统为 32 位用户态（`getconf LONG_BIT = 32`），Kaldi 跑在 armv7l 上很吃亏。
sherpa-onnx 的 int8 模型在这台机器上快 12 倍，可以真正流式实时。

## 「识别不准」怎么改的（2026-11-01）

认出来是能认，但**字错得厉害**。日志实录：

```
你说「用手势停车」 → 识别 '有用手术室停车' / '用手术室停车'
你说「打开手势」   → 识别 '爸开' / '大开' / '啊开始'
大量 ''            → 有声音，一个字都没出来
成片 [太短 0.00s]  → 环境噪声在反复触发 VAD
```

### 根因：用流式小模型做整句识别

这两条链路都是「VAD 切好一整句，再整段送进去识别」，根本没有"边说边出字"
的需求。而流式模型为了低延迟**不看后文**，参数又只有 14M，同音字只能靠蒙 ——
「手势」shou-shi 和「手术室」shou-shu-shi 差一个音，它分不清。
**用流式模型做离线识别，是纯亏。**

### 三条改动

| # | 改什么 | 效果 |
|---|---|---|
| 1 | 换成离线 paraformer-zh（217MB int8） | 整句一起看，中文词错率降一个档次 |
| 2 | 加 `asr_fix.py` 拼音纠正层 | 兜「手术室→手势」这类残余同音错 |
| 3 | VAD 阈值 0.5→0.55、静音 0.5→0.6 秒 | 噪声碎片少了，一句话不再被切两半 |

**耗时代价**（同一段 5.6 秒音频实测）：

| 模型 | 大小 | 解码 | RTF |
|---|---|---|---|
| 流式 zipformer 14M int8 | 78MB | 1.0s | 0.18 |
| 离线 paraformer int8 | 217MB | 2.37s | 0.42 |

按句子算：一句 2 秒的命令约 0.9 秒出结果。按住说话本来就要等一下，值得。
启动加载从 3 秒变成 **7.8 秒**（只在开机时一次）。

### 纠正层的两条边界（第一版就栽在这）

`asr_fix.py` 不是"把音近的都改掉"，那样会把句子改烂 —— 第一版实测把
「**帮我**打开手势」整句吃成了「打开手势」，把「手势停车」缩成了「停车」。

1. **已经正确的命令词是保护区。** 文本里凡是本身就和某个命令词完全一致的位置，
   一律标记保护，替换不许吃掉它；替换后还要检查被覆盖的词是否仍然存在。
2. **只有两字词才容忍一个音的偏差。** 「术室停车」和「手势停车」拼音只差一个
   字母，但那是四个字的片段，按音放过就会把整句拆坏。两字词没有上下文，
   错一个音就是真听错，反而该纠。

**只在按原意解析不出动作时才调用**（见 `hub.py` 的 `_resolve` 失败分支）。
原文能用就绝不碰 —— 这是最重要的约束，纠错层没有机会把对的话改错。

## 排障

- **耳机没声音**：`amixer -c 2 sset PCM 90% unmute`
- **麦克风没反应**：`python3 ~/miclevel.py 3`，峰值 <100 说明没采到
- **说话太轻识别不出**：实测峰值只有 -22dBFS 时整句会解码为空，
  正常说话应在 -12dBFS 左右。离麦近一点或提高音量。
- **`(有声音但没识别出内容)`**：VAD 触发了但解码为空，通常是杂音或声音太轻
- **爆音/断续**：调大 `PERIOD`、`BUF`
- **`Device or resource busy`**：USB 麦是独占的（`Subdevices: 1/1`），先
  `pkill -f '[t]alk\.py'` 再启动。注意 `pkill -f 'talk.py'` 会匹配到自己所在的
  SSH 命令行并把当前会话杀掉，必须写成 `[t]alk\.py`。
- **后台常驻**：`setsid -f timeout 900 python3 talk.py -q > ~/talk.log 2>&1 </dev/null`
  （普通 `nohup ... &` 会让 SSH 通道挂住不返回）

# 语音控车（小派 + 平衡车）

**零改线**：车上蓝牙模块本来就接在 STM32 的 USART2（PA2/PA3，9600 8N1），
树莓派通过 `rfcomm` 连上去，对车来说和手机 APP 没有任何区别。

**架构**：说 → VAD 切句 → sherpa 识别 → 本地意图表 → 蓝牙 → 车。
闭环放在车端（转向由车自己转到位），树莓派只用遥测判断"做完了没有"，
不参与控制，所以蓝牙那几十毫秒延迟不会让车抖动。

## 一、固件改动

只动 `PID_Car/6-代码优化/User/main.c`，`BlueSerial.c` 一个字没改。
原文件已备份为 `main.c.bak`，想退回去直接覆盖即可。

| 改动 | 内容 | 为什么 |
|---|---|---|
| 新增 `[go,v,w]` | 速度 + 转向直接下发，并**自动把 RunFlag 置 1** | 否则每次上电都得先按 Key1，语音喊破天车也不动 |
| 新增 `[turn,deg]` | 相对当前航向转 deg 度，正数右转 | 转向由车端闭环保证，不受蓝牙延迟影响 |
| 新增 `[stop]` | 速度/转向目标清零 | 刹车 |
| 新增航向角 `Yaw` | 对陀螺仪 GZ 积分，上电时静止 1 秒标定零偏 | 原来只用了 AX/AZ 算俯仰角，GZ 没积分，车根本不知道自己转了多少度 |
| 新增转向闭环 | 20Hz 跑 P 控制，误差 <3° 或超时 10s 就收手 | 让"右转 90 度"真的转 90 度 |
| 新增跌倒锁 `Fallen` | 角度超 ±50° 后锁死，语音指令**不能**再把它复活 | 原来跌倒停机后，下一句"前进"会立刻把车重新拉起来 |
| 遥测 `[s,...]` | 5Hz 回传俯仰角/速度/航向 | 支撑状态问答和"等它转完" |
| ~~`[plot,...]`~~ | **注释掉了** | 手机 APP 上的波形图会失效，换成遥测。想要波形就把注释恢复、注释掉遥测那行 |

## 二、烧录后第一次上电

**上电瞬间让小车静止约 1 秒**（OLED 亮之前）。这一步在标定陀螺仪零偏，
1 秒内别碰它，否则航向角会一直缓慢漂移，转向就不准了。

## 三、树莓派绑蓝牙串口

```bash
# 1. 打开 SPP 兼容模式（新版 BlueZ 默认关着，必踩的坑）
sudo sed -i 's|bluetoothd$|bluetoothd -C|' /etc/systemd/system/dbus-org.bluez.service
sudo sed -i '/bluetoothd -C/a ExecStartPost=/usr/bin/sdptool add SP' /etc/systemd/system/dbus-org.bluez.service
sudo systemctl daemon-reload && sudo systemctl restart bluetooth

# 2. 配对（打回车看提示，PIN 一般是 1234 或 0000）
bluetoothctl
  power on
  scan on                  # 找到你车的模块，记下 MAC
  pair AA:BB:CC:DD:EE:FF
  trust AA:BB:CC:DD:EE:FF
  exit

# 3. 绑成串口设备（这条会一直占着终端，正常）
sudo rfcomm connect hci0 AA:BB:CC:DD:EE:FF 1
```

> 手机 APP 和树莓派**不能同时连**，SPP 只允许一个连接。演示时把手机蓝牙关掉。

```
你：走一遍          →  它自己把这三步重演一遍
```

路线存在 `~/routes.json`，可以直接改文件。说「有哪些路」可以列出来。

**精度说明（答辩时别被问倒）**：
- 转向是**闭环**的（陀螺仪积分 + P 控制），所以角度能保证在 ±3° 左右；
- 前进是**开环**的（按时间算），地面打滑、电量不足都会让距离有偏差。
  想更准就得用编码器里程做闭环，那是下一步的事。

### 「原地转圈」为什么一开始拆两段、后来又不拆了

这是本次开发里一次完整的**先绕路再回来**，答辩讲这段比讲顺利的更有说服力。

**第一版：Pi 端拆两段。** 车端老固件转向闭环是硬超时 `YawTicks > 200`，20Hz 采样，
即最多转 10 秒。实测转速约 **56°/s**：

| 目标 | 理论耗时 | 10 秒够不够 |
|---|---|---|
| 90° | 1.6s | 绰绰有余 |
| 180° | 3.2s | 够 |
| 360° | **6.4s** | 只剩 3.6s 余量，起步一慢或地上有阻力就卡在半路 |

于是 Pi 端在 `turn_plan()` 里把超过 200° 的转向拆成 180°+180° 两段发。不用改固件、
不用担心截断，但**两段之间要停一次、重新闭环，转起来能明显看出一个"顿"**。

**第二版：改固件，超时按角度自适应。**

```c
#define TURN_TIMEOUT_TICKS(d)  ((uint16_t)(200.0f + fabs(d) * 1.8f))
```

56°/s 乘 1.8 倍余量，360° → 约 850 拍 ≈ 42 秒才收手。它只是"万一卡住了别一直转下去"
的保险 —— 正常转向都是靠 `fabs(err) < 3.0f` 到位停的，根本走不到超时分支。

同时把转向差速从 `avePWM ± difPWM/2` 改成 `avePWM ± difPWM`（`/2` 之后差速和平衡环
的抖动同一个量级，两轮会交替"停一下"，就是断续画弧），并加了最小差速 `TURN_MIN_DIF`
越过滤波死区、临近目标 `TURN_SLOW_K` 线性减速防冲过头。

现在 `turn_plan()` 原样返回一段，360° 一口气转完，中途按「停车」也能立刻停 ——
车端收到 `[stop]` 会把 `YawMode` 清零，闭环当场收手。

> 这段可以写进报告的"迭代过程"：**先在应用层绕过限制，验证功能可行性；再回到固件
> 消除限制本身。** 前者快，后者才对。

## 八点五、车停着会自己往前挪 —— 已修

**这是平衡车的典型病，不是你搭错了。** 有三个叠加原因，都改在了固件里：

| 原因 | 原代码 | 后果 | 已改 |
|---|---|---|---|
| **积分限幅被注释掉** | `PID.c` 里那行被 `//` 掉了，积分无上限累加 | 静止时速度误差在 0 附近抖动，累加后把角度目标慢慢推向一边，车就开始匀速漂 | 恢复限幅 |
| **限幅值写成正数** | `ErrorInt_max=100, ErrorInt_min=100`（应该是一正一负） | 即使取消注释，积分也会被钳成 ≥100，永远往一个方向 | `min` 改 `-100` |
| **低速测不出来** | 编码器 50ms 采一次，分辨率约 0.05 圈/秒 | 车以 3~4cm/s 挪动时速度环读数是 **0**，它压根不知道车在动 | 加位置环兜底 |

**新增的位置环**（`main.c` 20Hz 分支）：累加编码器里程，没有行进/转向意图时把车按在一个点上。
偏出 2mm 就出最小推力把它拉回来，偏出 6cm 就认为是被搬动过、重新锚定（不会硬拽）。
说"前进"或转向时自动解锁，不干扰正常动作。

### 调这个位置环

```c
Vtarget = perr * 4.0f;   // ← 回位快慢。车还在慢慢跑就加大(5~6)，来回点头就减小(2~3)
```

这里**故意没有设"最小推力"**。早期版本给它加了 0.25 圈/秒的最低速度来突破电机死区，
结果车在死区边缘反复点动，变成约 2Hz 的前后抖，比慢慢漂还难看。改成纯比例，稳。

### 如果改完还在漂，按这个顺序查

1. **看 OLED 的 `A:` 读数**。车静止立在平衡位置时，`A` 应该接近 0。
   如果稳定显示 `+2.0` 或 `-1.5`，说明 **MPU6050 装的零点偏了**，或者重心偏前/偏后 ——
   这才是车一直往前压的真实原因，位置环只是在硬拉。
   调法：把 `AnglePID.OutOffSet` 从 `3` 改到 `2` 或 `4`，各试一次，看哪边漂得轻。
2. **加大速度环 Kp**。默认 `2.1` 偏软：0.02 圈/秒的偏差只产生 0.04° 倾角，几乎没作用。
   改到 `3.5` 起步，还不稳就 `4.5`。**Ki 不要动**（0.02 已经够）。
3. **左右轮不一致**。如果车是"画着弧线"往前挪（不是直线），说明两个电机或编码器不对称。
   看 OLED 的 `LeftSpeed / RightSpeed`，静止时两边都应为 0；
   如果一直差一个固定值，把 `TurnPID.Kp` 从 `2` 加到 `3`。

> 提醒：改完 `PID.c` 和 `main.c` 都要**重新编译烧录**，只烧一个没用。

## 八点六、原地左右扭（车头小幅摆）—— 已修

**和"往前挪"是两回事**：往前挪是角度/速度环（前后方向），左右扭是转向环（绕竖直轴）。

### 根因：转向环积分饱和

原来的 `TurnPID` 是 `Kp=2, Ki=3`，积分限幅 `±20`：

```
积分项最大 = Ki × 限幅 = 3 × 20 = 60
输出上限 OutMax      = 50
```

**积分一满就直接顶穿输出上限。** 于是：车往左扭 → 扭过头 → 误差反向 → 积分慢慢退回来 →
退出饱和 → 又往右扭。形成一个自激极限环，周期约 1～3 秒，幅度不大但一直在摆。

这是串级 PID 里最典型的一类错误：**积分增益比比例增益还大**（Ki/Kp=1.5）。
位置式 PID 的 I 项系数一般应该比 P 小一个数量级。

### 改了三处

| 改动 | 前 | 后 | 作用 |
|---|---|---|---|
| `TurnPID.Ki` | `3` | `0.4` | 积分项最大只剩 2 个 PWM，不可能再顶穿上限 |
| `TurnPID` 积分限幅 | `±20` | `±5` | 双保险 |
| 轮速差死区 | 无 | `\|difSpeed\| < 0.05` 当 0 | 滤掉量化噪声，见下 |

### 第三条：为什么加轮速差死区

编码器 50ms 采一次，速度分辨率约 **0.05 圈/秒**，两个轮子相减后，
最小非零值也是 0.05。平衡车原地站立时轮子本来就在做前后微调，左右轮不同步，
产生的是**纯噪声**的速度差 —— 转向环把它当真去修正，车身就开始小幅度摆。

所以直接加死区：

```c
if (fabs(difSpeed) < 0.05f) { TurnPID.Actual0 = 0.0f; }
else                        { TurnPID.Actual0 = difSpeed; }
```

一句话概括：**低于传感器分辨率的信号不该进控制器**。这条原则比调 PID 参数重要。

---

### 走过的弯路：陀螺仪角速度阻尼（已关闭）

一开始还在 `difPWM` 上叠加了一个陀螺仪阻尼项：

```c
yawrate = (GZ - GZ_bias) / 32768 * 2000;   // 度/秒
difPWM  = TurnPID.Out - yawrate * YAW_DAMP;
```

思路是对的 —— 转向环只看编码器轮速差，50ms 采样、起转瞬间读数为 0，太慢；
MPU6050 的 GZ 是 100Hz / 16.4 LSB(°/s)，用它做阻尼属于"快传感器补慢传感器"。

**但实测下来，加了它车反而开始自己转。** 两个原因：

1. **零偏温漂**。`GZ_bias` 只在启动时标定一次，跑几分钟后 MPU6050 的零偏就可能漂
   几个 °/s。阻尼项会把"恒定角速度"当成"车在转"，换算成一个**恒定的转向推力**，
   车就一直朝一个方向慢慢转。
2. **符号依赖**。它要求 `difPWM` 与 `GZ` 的正负对应关系恰好正确，反了就是正反馈。

现在 `main.c` 顶部是 `#define YAW_DAMP 0.0f`，代码保留、默认关闭。
真要用，必须同时做**在线零偏跟踪**（车静止且没有转向意图时，用一阶低通持续更新
`GZ_bias`），并且先确认符号。

> 这一条可以直接写进报告：*"尝试了基于陀螺仪的角速度阻尼，实测发现零偏温漂会引入
> 稳态偏置，导致低速自转，遂改用轮速差死区方案。"* —— 比"一次就调好"可信得多。

## 八点七、原地转圈一顿一顿地画弧 —— 已修

现象：让它原地转 90°，轮子不是干净地一前一后，而是**一顿一顿地爬**，还带点画弧，
整体看着像"蹭着转"而不是"打着转"。

### 根因：差速和平衡输出同量级，互相吃掉

PWM 是这样合成的：

```c
LeftPWM  = avePWM - difPWM/2;
RightPWM = avePWM + difPWM/2;
```

`avePWM` 是**平衡环**的输出。平衡车静止站立时它不会老老实实待在 0，而是随姿态在
**±5~10** 之间持续抖动（它必须一直微调才能站住）。而 `difPWM` 是**转向环**输出，
被 `/2` 砍半后只有 ±12 左右 —— 两者是同一个量级。

于是发生的是：

| 时刻 | avePWM | 左轮 | 右轮 | 实际效果 |
|---|---|---|---|---|
| A | +8 | −2 | +18 | 左轮**几乎不转** |
| B | −8 | −18 | +2 | 右轮**几乎不转** |

两个轮子交替着"停一下"，叠加起来就是**断续画弧**，而不是原地打转。

第二层原因：电机有**静止摩擦死区**（PWM 大约 5 以下转不动）。转向环输出从 0 慢慢爬升，
在死区里爬的那段时间轮子完全不动，要等车身歪了被平衡环推一下才动 —— 这是"一顿"的另一半。

### 改了三处（都在 `main.c` 的 20Hz 分支）

```c
/* 1. 转向时差速全量叠加，不再 /2 —— 让差速显著大于 avePWM 的抖动 */
if (YawMode == 1) { LeftPWM = avePWM - difPWM; RightPWM = avePWM + difPWM; }
else              { LeftPWM = avePWM - difPWM/2; RightPWM = avePWM + difPWM/2; }

/* 2. 最小差速：越过摩擦死区，要转就一定转得动 */
#define TURN_MIN_DIF 10
if (YawMode == 1 && fabs(YawTarget - Yaw) > 4.0f
    && difPWM < TURN_MIN_DIF && difPWM > -TURN_MIN_DIF)
{
    difPWM = (YawTarget > Yaw) ? TURN_MIN_DIF : -TURN_MIN_DIF;
}

/* 3. 临近目标线性减速：最后 25° 把速度目标压下来，别冲过头再往回摆 */
if (fabs(err) < TURN_SLOW_DEG) { t = err * TURN_SLOW_K; }   // 25° / 0.09
```

第三条解释一下：原来是"满速冲到目标前 3° 才收手"，惯性会冲过目标，再反向纠正一次
—— 就是转到位置之后那一小下抖动。改成最后 25° 按比例降速，是**线性减速**而不是急停。

### 调参

三个宏在 `main.c` 顶部：

| 宏 | 默认 | 调大 | 调小 |
|---|---|---|---|
| `TURN_MIN_DIF` | 10 | 起步更有力，但可能有"窜一下" | 小了会回到爬行顿挫 |
| `TURN_SLOW_DEG` | 25° | 收尾更平滑，但最后一段变慢 | 小了还是会小抖一下 |
| `TURN_SLOW_K` | 0.09 | 收尾更快 | 收尾更慢更稳 |

改完要**重新烧录**（这几行在固件里，不是 Pi 上的）。

> 答辩可以说：*"原地转向的难点在于平衡环和转向环共用同一对电机的 PWM，两个控制器的
> 输出会互相抵消。解决办法是让转向差速显著大于平衡输出的抖动幅度，并补偿电机摩擦死区。"*

### 如果还在扭，继续查

1. **机械不对称**。把车架起来（轮子悬空），按 Key1，看两个轮子转速是否一样、
   是否有一个轮子转起来有周期性顿挫（轮胎变形、轴弯、编码器磁环偏心）。
   机械问题调参数永远调不好。
2. **地面**。瓷砖上比地毯上好；四个轮子不同时着地也会扭。
3. **`TurnPID.Kp` 从 2 降到 1.5**。牺牲一点转向响应换取平稳。

### 转向只转一点点：根因是符号约定冲突

现象：按 A/D 车只转**十几度**就停，两个方向都一样。

原因链：

1. `MPU6050` 的 Z 轴按右手定则，**逆时针（左转）为正**，所以右转时 `Yaw` 是**减小**的；
2. 但转向闭环写的是 `YawTarget = Yaw + d`（`d>0` 表示右转，期望 `Yaw` 增大）；
3. 于是闭环一发现"`Yaw` 朝反方向走了 15°"，就判定为正反馈，触发发散保护直接收手。

**两个方向都会触发同一个保护，所以左右都只转一点点。**

修法（三处，都在 `main.c`）：

| 改动 | 内容 |
|---|---|
| 航向积分取负号 | `Yaw -= (GZ-GZ_bias)/32768*2000*0.01`，让"正角度=右转"成立 |
| 转向 P 系数 0.10 → 0.30 | `0.10` 时最后 20° 只剩 2 个 PWM，推不动电机，会提前停在离目标十几度处 |
| **新增转向方向自校准** | 转出 4° 后自动判断航向该往哪边长，若装反了就把航向坐标整体翻面一次，之后永久记住 |

第三条是关键：**换车、换陀螺仪模块、芯片装反面都不用改代码**。
第一转向会有一点点"抽动"（4° 内完成翻面判定），之后就正常。

### 遥测新增状态位（第 5 个字段）

```
[s,俯仰角x10, 速度x100, 航向, 状态位]
状态位 = 运行中×1 + 转向中×2 + 跌倒锁定×4
```

`car.py --monitor` 会把它翻译成人话：

```
俯仰 +0.8°   速度 +0.00   航向 +3°   运行中
俯仰 +12.4°  速度 +0.10   航向 +48°  运行中 转向中
俯仰 +86.1°  速度 +0.00   航向 +48°  跌倒锁定(按Key1解) 躺着/倒了
```

**看到"跌倒锁定"就说明车倒了**，按 Key1 才能解。这也是判断"转一点点"到底是
符号问题、还是车倒了被锁的最快办法 —— 以前这两者在现象上一模一样。

### 播报把语音卡死十几秒（Overrun!!!）

现象：说「记住这条路」后屏幕出现

```
[示教] 开始记录
[SAPI 服务不可用: <urlopen error timed out
errun!!! (at least 17108.299 ms long)
```

**示教本身是好的**（第一行已经进入记录状态），坏的是播报。

原因：`tts.py` 默认 `engine="sapi"`，SAPI 跑在 PC 上（`192.168.137.1:8765`）。
PC 端服务没开时，`urlopen` 要等 **15 秒**才超时，接着退到 edge-tts 联网再失败，
合计 **17 秒**。这 17 秒里没人读麦克风，`arecord` 的缓冲区溢出，就是那句 `Overrun!!!`。

修法（`car.py` 三处）：

| 改动 | 作用 |
|---|---|
| 开机探一次 SAPI，2 秒超时 | 不通就直接用本机 `espeak`，不再等 15 秒 |
| `speak()` 放后台线程 | 播报再慢也不卡麦克风采集 |
| 播报期间识别到的句子丢弃 | 防止把自己的话当成指令（尤其 espeak 被麦克风收进去） |

想用自然一点的声音：**PC 上双击 `pc\启动语音服务.bat`**，重启脚本会自动切回 SAPI。
不启动也能用，只是 espeak 是机器人音。

### 触屏里说「记住这条路」没反应

现象：屏幕上的「语音控车」页，按住说完松手，屏上只闪一下"没听懂这句"，车一点动静都没有。

原因不是识别错了，是**示教逻辑根本不在 `parse_intent()` 里**：它原来写在 `car.py` 的
`handle()` 里，而触屏页（`hub.py` 的 `VoiceCarApp`）只调 `parse_intent()`。所以触屏那条路
永远匹配不到"记住"这两个字，掉进最后的"没听懂"。

修法：把判断抽成公共函数 `car.teach_intent()`，`car.py` 和 `hub.py` 都调它；
`VoiceCarApp._finish()` 里先判示教、再判车指令。顺手把关键词放宽了，不再是精确匹配
「记住这条路」，只要同时有"记"和"路/路线/记录"就算开始：

| 说法 | 结果 |
|---|---|
| 记住这条路 / 记住这条 / 记一下路 / 记录路线 / 记着这条路 | 开始录 |
| 记好了 / 记完了 / 结束记录 / 不用记了 | 停录存盘 |
| 走一遍 / 原路返回 / 再来一遍 / 走刚才 | 重走最近一条 |
| 走厨房那条路 / 回放路线2 | 点名重走 |
| 有哪些路 | 念一遍都存了什么 |

顺带修了个隐性 bug：`Routes` 构造时没设 `last`，重启后"走一遍"会用空名字查表，
而 `"" in k` 恒为真，永远是字典里的第一条。现在开机就指向最后存的那条。

## 八点八、问它天气，它说不知道

现象：问"今天天气怎么样"，它回"我窝在树莓派里看不到窗外呀"；问"现在几点"，
它答"大概六点多"（实际下午四点）。听着像在装傻，其实是**它在猜**。

### 根因：API 不带联网

模型有两种用法，很多人会混：

| 用法 | 能不能查实时信息 |
|---|---|
| DeepSeek 网页版 / App，点了「联网搜索」 | 能。但那是**产品外面套了一个搜索插件**：先搜网页，把结果塞进对话，再让模型总结 |
| 调 `api.deepseek.com/chat/completions` | **不能**。你发什么它看什么，模型只会用训练时学到的参数 |

我们这个项目走的是第二种。`ask_llm()` 里只发了 `system` + 对话历史，一个字的实时数据都没有。
而"今天几号""外面几度"这类信息**每秒都在变，训练数据再新也答不对**——它只能按语言习惯编一个
像模像样的答案，这就是"大概六点多"的来历。

> 答辩时可以这么说：*"大模型的知识是训练截止那天的快照，不是实时数据库。
> 所谓联网搜索，本质是外部先取数据、再喂给模型。我们自己做了一遍这件事。"*

### 改法：自己当那个"搜索插件"

每次提问前先取一次实时数据，拼进 `system`：

```python
system = 人设 + "\n【现场实况】现在是 2026年10月30日 周五 16:07；外面阴，21度，湿度61%…"
```

`chat.py` 新增三个东西：

| 函数 | 作用 | 缓存 |
|---|---|---|
| `_where()` | ip-api 定位，失败退成都 | 1 小时 |
| `quick_weather()` | open-meteo 当前天气 + 今日高低温 + 降雨概率 | 5 分钟 |
| `live_context(weather=None)` | 拼成一句话；外部有现成数据（屏幕的 `WeatherSvc`）就直接用，不重复请求 | — |

`ask_llm(history, cfg, live=None)` 多一个参数，`build_system()` 负责拼。
提示词末尾还写死了约束：**"这里没有的信息就直说不知道，不要编"**——这比让它自由发挥重要得多。

### 实测（同一台树莓派，同一个模型）

| 问 | 不注入实况 | 注入实况 |
|---|---|---|
| 今天天气怎么样 | 我窝在树莓派里看不到窗外呀，你那边晴不晴？ | 阴天，21度，风有点大，六米每秒，下雨概率一成八，出门带件外套呗。 |
| 现在几点了 | 我看看啊，现在大概六点多 | 现在下午四点零七分啦，该歇歇眼睛咯。 |
| 明天会下雨吗 | 我查不到天气呀，没联网呢，你看看窗外云多不多。 | 不知道呀，我只能看到今天的天气，明天的事可不敢乱猜。 |

第三行是关键：**知道自己不知道什么，比知道答案更难**。实况里只有今天的数据，它就不会去编明天。
"大概六点多"这种才是真正危险的——它不承认不知道，直接给了一个错的。

`hotwords.txt` 也补了「天 气」「几 点」「多 少 度」「会 下 雨 吗」，避免识别成谐音字。

> 顺带一提：屏幕上的天气页（`WeatherApp`）和这条链路共用同一份数据源，
> 所以屏上显示 21 度、嘴上说 21 度，不会打架。

### 为什么它老是三言两语

问深一点就发现它答得很浅，很容易以为是模型不行。其实不是模型的问题，是**我们自己把它的嘴捂住了**：

| 约束 | 写在哪 | 后果 |
|---|---|---|
| "每次回复不超过 40 个字" | `llm.json` 的 system | 复杂问题也硬压成一句话 |
| `max_tokens: 150` | `llm.json` | 大约 100 汉字就被硬截断 |
| "不要列表、不要 Markdown" | 人设 | 这条是必要的，因为话要念出来 |

前两条是为了 TTS 服务的：喊一句"往前走"，回 200 字谁也受不了。但问"平衡车为什么能站住"就不该给一句话。

所以按问题分两档，`chat.is_deep()` 判断：

```python
DEEP_WORDS = ("讲讲", "解释", "为什么", "原理", "区别", "是什么", "举个例子", …)
def is_deep(text):
    if len(text) >= 16:                      # 语音识别出一长串，多半不是在下指令
        return True
    return any(k in text for k in DEEP_WORDS)
```

| | 快答 | 讲解 |
|---|---|---|
| 触发 | 前进 / 几点 / 明天会下雨吗 | 为什么天是蓝的 / 讲讲 PID |
| system 追加 | — | "用 100 到 180 个字讲明白，带一个例子，不要分点" |
| `max_tokens` | 150 | 700 |
| `temperature` | 0.9（俏皮） | 0.6（有条理） |

实测同一句话的两种回答：

```
[快答] 平衡车为什么能站住（28字 860ms）
  靠里面那个陀螺仪，一歪它就赶紧往歪的方向跑，把你拉回来。

[讲解] 平衡车为什么能站住（142字 1501ms）
  平衡车能站住靠的是里面那个陀螺仪和加速度计，它们一直在测车身往哪边歪。
  你一往前倾，它就判断你要往前倒，马上让轮子往前转去追你的重心，把车身拉回来。
  就像你手指顶一根扫把，扫把往左倒你就把手指往左移，它就一直不倒。
  平衡车每秒做好几百次这种调整，所以你感觉它稳稳站着，其实一直在偷偷纠偏呢。
```

**代价是慢**：讲解模式 1.5 秒（多了 0.5 秒生成），TTS 念 142 字要二十多秒。
所以只在你明确问"为什么/讲讲"的时候才展开，喊指令永远是秒回。

顺带把预报补上了：`quick_weather()` 多取两天（`forecast_days=3`），

```
明天毛毛雨，15到20度，降雨概率69%；后天毛毛雨，15到19度，降雨概率81%
```

于是"明天要不要带伞"也能答了，不用再让它猜。

## 八点九、记住我是谁

对话历史只留最近 12 条（6 轮），重启就清空。可"我叫什么、我在做什么"这种话十年也不变，
每次都要重新介绍一遍太蠢。所以单独存一份 `memo.json`：

```json
{
  "name": "许鑫",
  "project": "智能桌宠"
}
```

每次提问前拼进 system：

```
【你记得关于主人的事】名字：许鑫；正在做的事：智能桌宠。
自然地用，不需要每条都复述，也别再问已经知道的事。
```

### 怎么记进去的

不靠模型自己判断要不要记（它会时记时不记，还爱记错），用几条正则从话里抽：

| 说的话 | 记下 |
|---|---|
| 我叫许鑫 / 我的名字是许鑫 | `name` |
| 我在做一个语音控制平衡车的项目 | `project`（尾部的"的项目"会削掉） |
| 我的毕设是智能桌宠 | `project` |
| 我在成都大学 | `school` |

抽到就立刻落盘（先写 `.tmp` 再 `os.replace`，断电不会留下半个 JSON）。
**先记再问**，所以说完"我叫许鑫"这一句，同一句的回答里它就已经叫得出名字了。

### 踩的坑：问句被当成自我介绍

第一版上线就翻车：问一句"我叫什么"，名字被改成了**"什么"**。

```
[记忆] 记下了 {'name': '什么'}      ← 灾难
```

因为 `我叫([\u4e00-\u9fa5]{2,4})` 和"我叫许鑫"长得一模一样，区别只在宾语是个疑问词。
修法是抽到之后先过一道：

```python
_QUESTION = ("什么", "啥", "谁", "哪", "多少", "几个", "怎样", "怎么", "干吗", "干嘛", "吗", "呢")
if any(q in val for q in _QUESTION):
    continue        # 这是在问，不是在告诉
```

同理排除"我叫你小派"（宾语带"你"）、"我叫车停下"（带"车"）。

### 忘掉

| 说 | 效果 |
|---|---|
| 忘掉我的名字 | 只清 `name` |
| 忘掉我的项目 | 只清 `project` |
| 清空记忆 / 全忘掉 | 全清 |

这几句**拦在模型前面**，不发给它。否则它会一边答应"好的我忘了"，一边 system 里还带着名字。

命令行也能管：

```bash
python3 chat.py --memo              # 看记住了什么
python3 chat.py --forget            # 全清
python3 chat.py --forget name       # 只清名字
```

### 实测（树莓派实机）

```
说：我叫张三              → [记忆] 记下了 {'name': '张三'}
                           → 小派：张三呀，这还能忘。
说：我叫什么              → 小派：张三呀，这还能忘。      （没再污染记忆）
说：我在做一个自动浇花系统   → 小派：知道，你之前说过。现在跑到哪一步了？
说：我在做什么            → 小派：你在弄自动浇花系统。
说：清空记忆              → 小派：好，我把记得的事全清掉了。   （1ms，没走模型）
```

**重启之后照样记得** —— 这就是它跟对话历史最大的区别。

> 为什么不用向量数据库：要记的是几个固定字段，不是一整段散文。
> 一个 JSON 加几条正则，比拉一个 embedding 模型进来省事得多，也更好解释。

## 九、排障

- **喊了前进车不动**：先看 OLED 右下角 `SpeedPID.Target` 有没有变。没变 = 蓝牙没通；
  变了但电机不转 = 按一下 Key1，或者车之前跌倒过被锁了（`Fallen`，只能按 Key1 解）
- **车停着自己往前挪**：见上面「八点五」，已经改好了
- **车原地左右扭（车头小幅摆）**：见「八点六」，转向环积分饱和 + 缺角速度阻尼，已改好
- **转向一直转不停**：陀螺仪零偏没标定好，重新上电、保持静止 1 秒
- **转向角度越走越偏**：GZ 积分必然有漂移，长时间跑需要中途"回正"——说一次
  「停」再走，或者把车抱起来转一圈让它自己重新对齐
- **`--monitor` 没数据**：`ls /dev/rfcomm0` 存不存在；`sudo rfcomm connect` 是不是断了
- **识别不出「右转」**：把 `hotwords.txt` 加上 `右 转`（每汉字空格隔开），
  改完重启脚本
- **说完话要等一两秒车才动**：这句没命中意图表，被送到 DeepSeek 慢通道了。
  看日志有没有「[模型不可用]」，或者加 `--no-llm` 强制纯本地
