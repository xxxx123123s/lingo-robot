从头看懂这套语音桌宠

不谈架构，只跟着一段声音走：它从麦克风出来时是什么样，到耳机里又变回了什么样。

空气振动你说"你好"
一串整数12800 个 int16
一串小数12800 个 float32
一句话"你好" (str)
一串整数WAV 文件字节
空气振动耳机里出声

整件事最反直觉的地方是：计算机不知道什么是"声音"。它只知道数字。所以这套程序干的活，全是在搬运和翻译数字——一共三次翻译：振动→数字、数字→文字、文字→数字。

02英语名词小词典

这些词你在代码和报错里会反复撞见。我给每个词都写清楚"它在这个项目里具体指哪一行代码"，比字典定义有用。

英文字面意思在这个项目里具体是什么
sample采样点声音的一个瞬间。1 秒采 16000 个点，所以代码里到处都是 16000 和 1600。
sample rate采样率每秒采多少个点。RATE = 16000，语音识别模型的硬性要求，不能改。
PCM / raw原始波形数据没有任何文件头，纯粹的数字流。arecord -t raw 就是输出这个。
int1616 位整数每个采样点用 2 字节存，范围 −32768～32767。S16_LE 里的 S16 就是这个意思。
chunk一块一次读多少。CHUNK = 1600 = 0.1 秒。程序是"一块一块"处理声音的，不是一次性。
buffer缓冲区声卡和应用之间的中转箱。--buffer-size=16000 就是 1 秒的容量。
VADVoice Activity Detection
人声活动检测		判断"这一小块里有没有人在说话"。它不识别内容，只回答是/否。模型文件 1.8 MB。
ASRAutomatic Speech Recognition
自动语音识别		把声音变成文字。这里用 sherpa-onnx。Vosk 也是 ASR，但太慢被换掉了。
TTSText To Speech
文字转语音		把文字变成声音。这里有三个后端：sapi / edge / espeak。
SAPISpeech APIWindows 自带的语音接口。你电脑里本来就装了中文女声，不用联网、不用密钥。
RTFReal Time Factor
实时率		处理 1 秒音频需要几秒。小于 1 才能用。Vosk 是 1.98（说完要等两倍时间），sherpa 是 0.18（快 5 倍多）。
preroll预先滚动录音时总是"先说后录"，VAD 反应过来时第一个字已经过去了。preroll 就是把之前 0.35 秒也补上。见 talk.py 195 行。
hotword热词你希望它优先认对的词。你的人名"许鑫"就在 hotwords.txt 里。
carry余数 / 结转VAD 每次只吃 512 个点，但一次读到 1600 个。1600 除不尽 512，剩 64 个要留到下一次。见 talk.py 200 行。
stream流识别引擎的工作台。一次识别要新建一个 stream，喂数据，拿结果。见 talk.py 134 行。
endpoint端点一句话的结束位置。旧版本靠它断句，现在改用 VAD 了。
normalize归一化把 −32768～32767 的整数除 32768，变成 −1.0～1.0 的小数。模型只吃这种格式。
LLMLarge Language Model
大语言模型		这里的 DeepSeek。
token词元模型计费单位。max_tokens: 150 = 最多回 150 个词元，防止它长篇大论。
system prompt系统提示词给大模型定人格的那段话，规定它是"小派"、不超过 40 字、不许用表情符号。
plughw:3,0设备名3 是声卡编号（USB 麦克风），0 是这块卡上的第几个设备。plughw:2,0 是板载 3.5mm 口。
asymasymmetric
不对称		ALSA 的一种虚拟设备：播放走一个声卡，录音走另一个。.asoundrc 里就这么配的。

03一步一步走一遍

从现在开始，假设你对着麦克风说了一句"你好小派"，时长约 0.8 秒。跟着它走。下面的行号都是 /home/pi/talk.py 的真实行号。

1
打开麦克风，让它一直往外吐数据
talk.py 174–177

程序不"录一段停下来"，而是启动一个叫 arecord 的系统程序，让它像个水龙头一样不停往外流。

cmd = ["arecord", "-D", args.device, "-f", "S16_LE", "-r", "16000",
       "-c", "1", "-t", "raw", "-q",
       "--period-size=1600", "--buffer-size=16000"]
proc = subprocess.Popen(cmd, stdout=subprocess.PIPE, bufsize=0)
参数含义
-f S16_LE 每个点 2 字节小端序 · -r 16000 每秒 16000 点 · -c 1 单声道 · -t raw 不要文件头
输出
一个管道 fd，可以从里面读字节
2
每次抓 0.1 秒的字节
talk.py 187
d = os.read(fd, CHUNK * 2)   # CHUNK=1600，乘 2 是因为一个点 2 字节

这次读到的是 3200 个字节。它们在内存里长这样（十六进制，前 8 个）：

03 00 f5 ff 1a 00 b2 ff …… 共 3200 字节

单看这堆东西，你完全不知道它是声音还是图片。只有"约定"才让它成为声音——约定的内容就是：每 2 字节算一个数，每秒 16000 个。

3
字节 → 整数 → 小数（两次变形，一行代码）
talk.py 190
samples = np.frombuffer(data, dtype=np.int16).astype(np.float32) / 32768.0

这一行干了三件事，从左往右读：

frombuffer(data, int16)把那 3200 个字节按"每 2 字节一个整数"读出来[3, -11, 26, -78, ...]
astype(float32)整数转成浮点，为下一步除法做准备[3.0, -11.0, 26.0, -78.0, ...]
/ 32768.0全部除以 32768，压到 −1～1 之间[0.0001, -0.0003, 0.0008, -0.0024, ...]
为什么要除 32768？识别模型和 VAD 模型都是在"−1 到 1 的浮点数"上训练的。你直接喂 3 万这种大整数，它只会输出乱码。这一步没有捷径，是硬规定。
4
把 1600 个点"零敲碎打"喂给 VAD
talk.py 200–203

这里有个很隐蔽的坑。你每次拿到 1600 个点，但 VAD 每次只肯吃 512 个。1600 = 512 × 3 + 64，除不尽，会剩 64 个。

carry = np.concatenate([carry, samples]) if len(carry) else samples
while len(carry) >= window:
    vad.accept_waveform(carry[:window])
    carry = carry[window:]
第 1 次读入 1600 个 → 喂 512×3，剩 carry = 64 个
第 2 次读入 1600 个 → carry 变 1664 → 喂 512×3，剩 carry = 128 个
第 3 次读入 1600 个 → carry 变 1728 → 喂 512×3，剩 carry = 192 个
……这样一直滚下去，一个点都不丢
如果不写 carry 会怎样？每块都丢那 64 个点。1600 里丢 64 = 丢掉 4% 的音频。听起来不多，但丢的是连续的小碎片，识别结果就会时不时错一个字——而且你根本查不出原因。这一行是踩过坑之后补的。
5
VAD 回答一个问题：现在有人说话吗？
talk.py 210
if buf is None and vad.is_speech_detected():
    buf = hist.copy()
    just_started = True

vad.is_speech_detected() 只返回 True 或 False。没说话的时候它一直返回 False，这一块数据就直接扔了——不识别、不打印、不理会。

这正是当初治好"乱出字"的关键。以前没有 VAD，风扇声、敲键盘声都被送去识别，模型硬凑出"嗯""那个"这种字。

buf
装"当前这句话"的容器。之前是 None（空的），现在被赋上了一段真实数据，从此开始累积。
6
补上说话前的 0.35 秒
talk.py 195、205–207、211

VAD 从"检测到人声"到"真正反应过来"之间有延迟。等你确认有人说话，第一个"你"字已经过去了。所以程序一直在偷偷保存"最近 0.35 秒"，一旦人声出现，就把这段历史也塞进去。

preroll = int(0.35 * RATE)        # = 5600 个点
# 每块都往 hist 里追加，并只保留最近 5600 个
hist = np.concatenate([hist, samples])
if len(hist) > preroll:
    hist = hist[-preroll:]
# 人声出现的那一刻：
buf = hist.copy()                 # 历史 5600 个 + 从现在开始累积
buf 的组成：
[ 之前的 0.35 秒静音/气声 ][ 第 1 块 ][ 第 2 块 ][ 第 3 块 ]……
↑ 这份才让"你"字没被切掉
7
VAD 说"这句说完了"，交出一整段
talk.py 216–224
if not vad.empty():
    seg = buf if buf is not None else vad.front.samples
    if speech_seconds(seg) >= 0.3:      # 太短的多半是杂音
        handle(recognize(seg), seg)
    buf = None                          # 清空，准备下一句

停顿 0.5 秒后 VAD 认为说完了。seg 现在是一个约 12800 个 float32 的数组，也就是你要识别的整句话。

那个 speech_seconds(seg) >= 0.3 是干嘛的？它算这段里"真正有声音"的秒数。之前有一次你说"帮我打开台灯"，录音峰值只有 −22 dBFS、实际发声 0.3 秒不到，识别结果完全跑偏。加上这道门槛后，这种"说得太轻"的片段会被直接丢掉，不会给你一个莫名其妙的回答。
8
数字 → 文字
talk.py 133–139
def recognize(samples):
    s = rec.create_stream()              # 新建一个识别工作台
    s.accept_waveform(RATE, samples)     # 把整段音频喂进去
    s.input_finished()                   # 告诉它：音频给完了
    while rec.is_ready(s):
        rec.decode_stream(s)             # 反复解码直到解不动
    return rec.get_result(s).strip()     # 取出文字
输入：array([0.0001, -0.0003, ..., 0.012], dtype=float32) 12800 个
输出："你好小派" str，4 个字符

注意 input_finished() 是写在 s 上的（stream），不是写在 rec 上的（recognizer）。这里当初写错过一次，报错找了很久。

这一步耗时约 0.7 秒。之所以能这么快，是因为模型只有 14 MB——用的是 streaming-zipformer-zh-14M，那个 "-14M" 就是参数量级别。

9
文字 → 文字（这一步只在 chat.py 里有）
chat.py 72–89

talk.py 到第 8 步就结束了——它拿到文字直接念出来，所以叫"复读机"。chat.py 在中间插了一步：把文字发给 DeepSeek。

body = {
    "model": cfg["model"],
    "messages": [{"role": "system", "content": cfg["system"]}] + history,
    "temperature": 0.9,
    "max_tokens": 150,
    "stream": False,
}

发给 DeepSeek 的其实是一个完整对话清单：第一行是人格设定，后面是你俩之前说过的 12 条消息（6 轮）。这就是它"能记住上下文"的全部秘密——每次请求都把历史重发一遍，模型本身不记得任何东西。

messages = [
  {"role":"system",   "content":"你是一只住在树莓派里的小桌宠……"},
  {"role":"user",     "content":"你好小派"},
  {"role":"assistant", "content":"哎，我在呢！"},
  {"role":"user",     "content":"今天几号"}
]

返回约 0.2 秒，得到一句新文字，比如 "我哪知道呀，我又没有日历。"

但它回来的不是纯字符串，是三层壳。真实结构大概是这样：

{
  "id": "chatcmpl-8f2a...",
  "model": "deepseek-chat",
  "choices": [
    { "index": 0,
      "message": { "role": "assistant", "content": "哎，我在呢！有啥事？" },
      "finish_reason": "stop" }
  ],
  "usage": { "prompt_tokens": 156, "completion_tokens": 12, "total_tokens": 168 }
}

所以要剥三层才拿到那句话，对应 chat.py:88-89：

raw  = r.read()                                    # 1. bytes  原始字节
text = raw.decode("utf-8")                         # 2. str    JSON 文本
data = json.loads(text)                            # 3. dict   Python 字典
answer = data["choices"][0]["message"]["content"]  # 4. str    真正那句话
字段用途
usage.total_tokens计费依据，你花的钱按这个算
finish_reason: "stop"正常说完了
finish_reason: "length"被 max_tokens 掐断了，回答是半句。这时念出来像突然卡住，把 llm.json 的 max_tokens 调大即可
choices 为什么是数组理论上可以一次要好几个候选（n 参数），默认只给 1 个，所以永远取 [0]
"stream": False攒齐了一次返回。改成 True 会变成一行行 data: {...} 碎片，响应更快但要边收边拼
10
文字 → 数字 → 声音
tts.py 50–61

树莓派自己念不好听，所以它把文字发到你的电脑上去合成，再把 WAV 取回来自己播。

def _sapi_wav(text, voice, rate, timeout=15):
    q = urllib.parse.urlencode({"text": text, "voice": voice, "rate": rate})
    with urllib.request.urlopen(f"{SAPI_URL}/tts?{q}", timeout=timeout) as r:
        return r.read()

实际发出去的 HTTP 请求，浏览器里也能打开：

GET http://192.168.137.1:8765/tts?text=我哪知道呀&voice=huihui&rate=180

电脑那边（pc/tts_server.py）收到后：

eng = pyttsx3.init()
eng.setProperty("voice", vid)      # 选中 Huihui 中文女声
eng.setProperty("rate", rate)     # 语速 180
eng.save_to_file(text, path)       # 写成临时 wav
eng.runAndWait()
return open(path, "rb").read()       # 把 wav 的字节原样回传

树莓派拿到字节，存成 /tmp/tts_sapi.wav，最后一步：

return subprocess.run(["aplay", "-D", out, "-q", path]).returncode == 0

aplay 是 arecord 的镜像工具——一个录、一个放。-D plughw:2,0 指定从 3.5mm 耳机口出来。到这里，数字又变回了振动。

04逐个文件解剖

每个文件我都只回答三个问题：它接收什么、它吐出什么、谁在调用它。别的都是次要的。

talk.py 复读机，也是全项目的"基础库"

接收：麦克风的字节流（或一个 wav 文件）
吐出：屏幕上的文字 + 耳机里的声音
运行：python3 talk.py

这个文件有两个身份，这点最容易搞混：

① 直接运行时，它是完整的复读机。
② 被 chat.py 引入时，它只贡献四个函数，自己不会跑起来（因为底部有 if __name__ == "__main__" 挡着）：

导出的东西是什么
make_rec()造一个识别引擎（加载 3 个 onnx 文件）
make_vad()造一个人声检测器
speech_seconds()算"真正有声"的秒数
MODEL / VAD_MODEL / RATE三个常量，路径和采样率

所以改识别相关的任何参数（模型、热词、VAD 灵敏度），改 talk.py 一处，两个模式同时生效。

chat.py 对话版，比 talk.py 多一个大模型

接收：同上
吐出：文字回答 + 语音
运行：python3 chat.py

它和 talk.py 的第 1～8 步代码几乎是复制来的（VAD 那套逻辑一模一样），区别在第 9 步：

from talk import make_rec, make_vad, speech_seconds, MODEL, VAD_MODEL, RATE

识别部分直接 import，但主循环是重写的——因为 talk.py 的主循环写死了"识别完就念"，没法插入大模型。这是当初为了快速验证而复制的，不算优雅但很清楚。

文件里唯一值得单独说的是 reply_to()：

def reply_to(text):
    history.append({"role": "user", "content": text})
    if len(history) > HISTORY_MAX:      # 12 条 = 6 轮
        del history[:-HISTORY_MAX]        # 超了就把最老的扔掉
    answer = ask_llm(history, cfg)
    history.append({"role": "assistant", "content": answer})

这就是"记忆力"的实现：一个普通列表，超长就砍头。没有数据库，没有向量检索，就 12 条消息。

tts.py 单一的语音出口，带三级降级

接收：一段文字 str + 目标声卡
吐出：耳机里的声音（没有返回值）
被谁调用：talk.py 和 chat.py

降级链是它的全部价值：

顺序引擎快不快什么时候轮到它
1sapi（PC）0.17 秒默认。HTTP 失败或返回不足 1000 字节就往下掉
2edge（微软在线）1～3 秒音质最好，但国内十次成两次。试 2 次
3espeak（本机）0.05 秒永远能用，永远难听。兜底

还有个细节在 clean()：

text = re.sub(r"[*#`_>\[\]{}()~|]", " ", text)   # 去掉 markdown 符号
text = re.sub(r"[\U0001F000-\U0001FAFF...]", "", text)  # 去掉表情符号

因为大模型很爱输出 **重点** 和表情，而这些被念出来就是"星号星号重点星号星号"。这层过滤是必须的。

为什么嗓子必须挂在 PC 上 不是设计偏好，是被文件格式和实测数据逼的

你在 Windows 上听到的那个女声，全部素材就躺在这里，一共 77 MB：

C:\Windows\Speech_OneCore\Engines\TTS\zh-CN\
  M2052Huihui.apm    6.0M   # huihui 这个嗓子的声学素材
  M2052Hongyu.APM    6.5M   # 男声 hongyu
  M2052Huihui.ini    732B   # 参数

.apm 是微软私有格式，Linux 上没有任何引擎读得了。所以不是不想在树莓派上跑，是这份料搬不走。能搬的只有替代品，而替代品全试过了：

放在哪声音从哪来实测为什么没用
树莓派 espeak内置共振峰算法，没有语音库0.05 秒，机械感极强"一个字一个字念出来不好听"
树莓派 edge-tts微软在线服务1～3 秒，Pi 上 10 次成 2 次网络一抖就没声
树莓派本地 VITSmelo-tts 模型，几百 MBRTF 17～23，3 秒的话要算 50 秒以上慢到没法对话
PC SAPI系统自带 77 MB 中文语音库0.14 秒现在用的

反过来，树莓派上的东西也搬不过来：21 MB 的 .onnx 识别模型 PC 能跑，但麦克风插在树莓派上，声音在那儿出生，所以识别只能留在原地。谁手上有料，谁干活。

另一层原因更实际：树莓派是靠这台 PC 的热点上网的（192.168.137.1 就是 PC），PC 本来就必须开着，把嗓子挂上去是零新增依赖。

06三个奇怪的设计为什么存在

代码里有三处看起来"多余"的东西。它们全都是踩坑之后补的，删掉就会退回到原来的问题。

carry：为了不丢那 4%

1600 除 512 余 64。不写 carry，每块丢 64 个点，也就是每 0.1 秒丢 4 毫秒。这些碎片是连续的，正好落在音节中间时会把字切碎。症状是"识别时不时错一个字，但重说一遍又对了"——极难排查。

preroll：为了不丢第一个字

VAD 需要积累几百毫秒才能确信"有人在说话"。等你确信了，第一个字已经流过去了。所以必须一直留一份 0.35 秒的历史。但要注意：preroll 只能救"被切掉"的字，救不了"模型本身认不出"的字。当初"今天"变成"天"就是后者，用 seginfo.py 三个裁剪点一测就分清了。

speech_seconds 门槛：为了不出洋相

有些片段 VAD 认为是人声（确实有点声音），但实际只有 0.2 秒的有效内容。这种片段送进识别，模型会硬凑出一个词，然后大模型一本正经地回答一个你根本没问的问题。加上 ≥ 0.3 秒的门槛，这类片段直接丢弃，屏幕上什么都不显示——比瞎答好。

08ASR 到底怎么认字

这一节回答一个最自然的猜想：是不是有个中文库，每块数据对应一个字，找到就拼成一句话？库里确实有，但认字的机制和这个猜想差得比较远。

先把这几步分开，别焊在一起

看图时最容易犯的错，是把"换单位""切格""打分"当成同一件事，也容易以为"后面都是对字节处理"。它们发生的时间、地点、执行者全都不同：

动作在哪做了什么数量变化谁干的
换能麦克风头声压 → 微弱电压（毫伏级），纯物理—电容振膜
量化USB 声卡芯片电压 → 字节，每秒量 16000 次，每次 2 字节— → 32000 字节/秒ADC
换单位talk.py:190int16 整数 → float32 小数，内容一模一样12800 → 12800你自己的 Python 代码
切帧模型内部10 毫秒一帧，每帧算 80 维频谱12800 → 6400sherpa 的 C++ 特征提取
切格encoder 内部4 帧合成 1 格80 帧 → 20 格encoder 神经网络
打分joiner 内部每格对 5539 个符号各打一个分20 → 110780 个分数joiner 神经网络
塌缩解码器逻辑每格只留赢家，空白丢弃，相同的合并110780 → 4 个字beam search 算法
字节只是运输格式，不是工作格式。字节只在 os.read() 拿到手、到 np.frombuffer() 解开之间存活几微秒。talk.py:190 执行完，它永久变成 float32 数组，后面再没有任何一行代码见过"字节"。
别漏掉特征提取这一层。float32 波形不是直接进 encoder 的。中间隔着 sherpa 的 C++，把波形转成 80 维频谱——这一层不是神经网络，是纯数学（傅里叶变换 + 滤波器组），藏在 accept_waveform() 里面，看不见也改不了。

为什么"说得太轻"就认不出

ADC 是 16 位的，等于把电压切成 65536 个台阶。正常音量时你的声音在台阶高处、底噪在低处，两者分得开；说得太轻时，声音和底噪掉进同一个台阶区间，ADC 在量化那一刻就已经分不开了——后面再聪明的模型也救不回来。这就是当初 miclevel.py 测出 −22 dBFS 时需要提高音量的根本原因。

词表的真面目

路径 /home/pi/sherpa-onnx-streaming-zipformer-zh-14M-2023-02-23/tokens.txt，共 5539 行，48 KB，格式是"字 + 空格 + 编号"：

<blk> 0        ← 空白。最重要的一个符号，下面会讲
<sos/eos> 1    ← 句子开始 / 结束
<unk> 2        ← 不认识
怎 3
么 4
样 5
...
你 69
好 17
小 405
派 907
许 119
鑫 3784      ← 排在三千多位，罕见字
注意编号不是按拼音也不是按笔画排的。它是训练时按词频统计出来的顺序：越靠前的字在语料里出现得越多。所以编号本身携带信息——鑫 的 3784 这个位置，就是它老被认错的伏笔。

第一步：波形被扔掉，换成频谱

模型根本不吃你那 1600 个采样点。它先把音频重新处理一遍：

动作具体参数结果
分帧窗口 25 毫秒，每帧往前挪 10 毫秒1 秒 → 100 帧
算频谱每帧算 80 维滤波器组能量（fbank）每帧 80 个数
合计100 × 801 秒音频 → 8000 个数

这一步的意义是丢掉波形、只留频率构成。人耳分辨"你"和"泥"靠的本来就是频率分布，不是波形的长相。到这一步，你程序里"1600 个点一块"的概念就彻底消失了——分块只影响搬运，不影响识别。你把音频按 0.13 秒切还是 0.07 秒切，结果完全一样。

第二步：三个网络，各有分工

文件大小它负责什么打个比方
encoder...int8.onnx21 MB看当前这段声音是什么，并结合前后文修正。做 4 倍下采样，每 40 毫秒输出一个向量耳朵
decoder...int8.onnx1.9 MB记住"刚才已经说出过哪些字"，压成一个状态短期记忆
joiner...int8.onnx1.8 MB把"听到的"和"说到哪了"合成一起，给 5539 个符号各打一个分拍板的人

所以每一格（40 毫秒）都会产生 5539 个分数。你说"你好小派"时，某一格的前几名大概是这样：

你   0.71  ← 选它
以   0.06
一   0.05
<blk> 0.04
异   0.01
…… 其余 5534 个接近 0

网络肚子里到底在算什么

把它当黑箱太可惜了——它内部其实只做两件事：加权求和，然后把负数压掉。重复几十层。

# 一个神经元干的全部事情（80 个输入简化成 3 个）
频谱 = [10, 90, 20]
权重 = [0.1, 0.8, 0.2]
结果 = 10*0.1 + 90*0.8 + 20*0.2  # = 77

那个 0.8 就是"关注重点"：它说明这个神经元最在意第二格。第二格能量一高，它就兴奋。旁边另一个神经元可能是 [0.0, 0.1, 0.9]，专盯第三格。

问题答案
为什么要几十层？单层只能看"某几格高不高"，叠起来才能看"形状"。像认脸：第一层看到有边缘，第二层看到有弧线，第三层认出是鼻子
21 MB 是什么？就是这些权重的总量。14M 指约 1400 万个权重数字。文件名里的 int8 是把每个权重从 4 字节压成 1 字节，所以 encoder 从 40 MB 缩到 21 MB
训练在干什么？喂几万小时录音、每段标好字，让它自己调那 1400 万个权重直到猜对。没人告诉它每个神经元该负责什么，这个分工是它自己找出来的
打开 onnx 能看到规则吗？看不到。里面全是数字，没有任何人类可读的规则
一句话：神经网络不认识字，它认识频谱的图案；它不知道规则，它只有几百万个调好的权重。所以"今天→天"这种错，不是逻辑写错了，是权重不够多、图案分不开。

第三步：大部分时候它输出的是"空白"

这是最反直觉的一点。<blk> 不是错误，是正常输出。0.8 秒的"你好小派"约 20 格，其中 16 格吐的是 <blk>，只有 4 格吐字。

格1 格2 格3 ... 格5 格6 ... 格9 格10 ... 格16 格17 ...
<blk> <blk> <blk> … 你 <blk> … 好 <blk> … 小 <blk> … 派 …

所以你猜的"组成一段话"，机制上是边听边吐、吐出来按顺序接上，不是先找齐所有字再拼。而你那句 get_result()，拿到的就是这个已经累积好的序列。

第四步：两种决策方式，决定了热词能不能生效

方式怎么定特点
greedy_search
贪婪搜索		每格只取分数最高的一个，不留备选快，但错了没得回头。没法加热词

改进束搜索		同时保留多条候选路径（如"许新"和"许鑫"并行），走完比总分慢一点，但能纠错，热词只能在这里生效

这就解释了 talk.py 第 56～58 行为什么要判断有没有热词文件：

if hotwords_file and os.path.exists(hotwords_file):
    method = "modified_beam_search"   # 有热词就必须切到这个
    kw = dict(hotwords_file=hotwords_file, hotwords_score=2.0)

热词的作用方式就是给指定路径补分。0.71 分的"新"和 0.09 分的"鑫"，加上 hotwords_score=2.0 之后天平就翻了。

两个老问题，现在可以定性了

现象本质能不能修

这两件事长得像，本质完全不同。判断方法就是当初 seginfo.py 干的事：同一段录音，在 0 / 0.2 / 0.35 秒三个位置裁剪后重新解码，如果结果一样，说明字本来就不在模型的判断里，跟录音裁剪无关。

中文的一个特殊便利

中文的 ASR 词表约等于音节表——一个汉字一个音节，一字一编号，所以看起来特别像"查字典"。英文不是这样：英文词表存的是 BPE 碎片（如 ▁hello 被拆成几块），一个词对应多个编号，需要拼。你觉得"一字一编号"很整齐，这是中文独有的。

如果只记一句话：这套程序没有"懂"声音，它只是把一串数字翻译成文字、再翻译回数字。所有的复杂度都不在逻辑上，而在那些数字的边界条件上——1600 除不尽 512、VAD 慢半拍、模型认不出轻声。这三件事占了全部调试时间的八成。
