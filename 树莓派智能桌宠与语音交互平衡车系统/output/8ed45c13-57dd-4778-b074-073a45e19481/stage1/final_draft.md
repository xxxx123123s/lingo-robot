# 树莓派智能桌宠与语音交互平衡车系统

## 摘要

本项目以树莓派 4B 为上位机、STM32F103 平衡车为下位机，通过蓝牙串口构建了一套「语音交互 + 触摸屏操控」的机器人系统。系统实现了三项核心能力：一是**用嘴开车**——说出"前进""右转九十度"即可控制平衡车，并支持"教一遍就自己重走"的示教再现；二是**一个有记忆的对话助手**——接入大语言模型并注入实时天气与本机时间，能回答"现在几度""我在做什么项目"这类需要实时数据和长期记忆的问题；三是**一块 2.4 寸触摸屏控制中心**——把对话、天气、遥控、语音控车、系统监控集成到同一界面。

实测转向平均绝对误差 3.3°，90° 转向耗时 1.6 秒；带实时天气的问答响应 1.0 秒；CPU 温控风扇在满占空比下连续采样 220 次无一次欠压。项目从零搭建，硬件未做任何破坏性改动，车端固件改动集中在单个文件中，可随时回退到原始版本。

---

## 一、项目背景与目标

平衡车是常见的嵌入式课程载体，但绝大多数实现停留在"能站住、能用手机 APP 遥控"的层次。手机遥控的问题很直接：操作者必须一手持机、一手扶车，双手被完全占用，既不能同时做别的事，也无法在远处观察车的姿态。

本项目的出发点是把交互方式从"手指"换成"语言"，让车从"遥控玩具"变成"可以指挥的机器人"。具体设定了四个目标：

1. **语音控车**：说出运动意图即可执行，不需要手机；
2. **双向通信**：车能把自己的姿态、速度、航向报回来，用语音念给用户听；
3. **示教再现**：演示一遍路径后，车能记住并复现；
4. **一体化交互**：所有功能收敛到一块触摸屏上，脱离电脑也能独立运行。

第四点是本项目区别于同类作品的地方——大部分语音小车仍然依赖电脑端运行识别程序，本项目把语音识别、大模型对话、界面渲染全部跑在树莓派上，开机即用。

## 二、系统总体设计

系统采用上下位机架构：树莓派负责"听懂"和"呈现"，平衡车负责"走准"。

```
        ┌──────────── 树莓派 4B（上位机）────────────┐
        │  麦克风 → VAD 切句 → sherpa-onnx 识别       │
        │              ↓                              │
        │  意图解析（本地规则）  ←→  DeepSeek 大模型   │
        │              ↓                              │
        │  动作白名单 → 蓝牙 SPP 下发                 │
        │              ↑                              │
        │  触摸屏 UI（6 个功能页）   遥测回传          │
        └──────────────┼──────────────────────────────┘
                       │ 蓝牙串口 9600 8N1
        ┌──────────────┼──────────────────────────────┐
        │              ↓                              │
        │  HC-04 → USART2 → 指令解析 → 串级 PID        │
        │                     ↑                       │
        │  MPU6050 航向积分 + 转向闭环 + 跌倒锁         │
        └──────────── 平衡车（下位机）────────────────┘
```

### 2.1 最关键的一个设计决定：转向闭环放在车端

树莓派**只下发意图，不参与控制**。它说"右转 90°"，车自己用陀螺仪积分转到 90° 才停。

理由是蓝牙链路有 50～100 ms 延迟且会抖动。如果让树莓派做闭环，每一拍控制量都带着延迟和抖动进入系统，车会来回振荡。**把闭环放在被控对象一侧，通信延迟就从"控制回路的一部分"退化成"命令何时开始"，不影响稳定性。** 这也是许多同类项目失效的根源：把 PID 放在上位机，蓝牙一拥堵车就抖。

### 2.2 通信协议

报文用方括号包裹、逗号分隔，兼容平衡车原有的手机 APP 格式，因此车端不需要为语音功能改协议。

| 方向 | 报文 | 含义 |
|---|---|---|
| 上位机 → 车 | `[go,速度,转向]` | 例如 `[go,1.40,0]` 前进 |
| 上位机 → 车 | `[turn,角度]` | 例如 `[turn,90]` 右转 90° |
| 上位机 → 车 | `[stop]` | 立即停车 |
| 车 → 上位机 | `[s,俯仰×10,速度×100,航向,状态]` | 20 Hz 遥测 |

状态位 = 运行中×1 + 转向中×2 + 跌倒锁定×4 + 陀螺仪异常×8。设置状态位的目的是**远程区分故障**："车倒了被锁死"和"转向闭环没收敛"在外部现象上几乎一样，都只动一点点，没有状态位时只能靠猜。

## 三、硬件组成

| 模块 | 型号 / 规格 | 作用 |
|---|---|---|
| 上位机 | 树莓派 4B（8 GB） | 语音识别、大模型对话、界面渲染 |
| 下位机 | STM32F103C8T6 | 姿态解算、串级 PID、电机控制 |
| 姿态传感器 | MPU6050 | 取 Z 轴角速度做航向积分 |
| 编码器 | 双霍尔 44 线 | 速度与里程反馈 |
| 电机驱动 | TB6612 | 双路电机 PWM 驱动 |
| 蓝牙模块 | HC-04 | 经典蓝牙 SPP 透传，免驱动 |
| 显示屏 | ST7789，240×320，SPI 触摸 | 一体化交互界面 |
| 音频 | USB 麦克风 + 3.5 mm 音箱 | 语音输入输出 |
| 散热 | TB6612 + 5 V 小马达 | CPU 温控风扇 |

需要特别说明的是**接线未做任何破坏性改动**。蓝牙模块原本就接在 USART2 上供手机 APP 使用，树莓派连上去之后，对车而言与手机完全等价。这是本项目能够快速推进的前提——车端的既有功能一条都没有被破坏。

## 四、功能实现

### 4.1 语音对话助手

对话链路为：麦克风采集 → VAD 静音检测切句 → sherpa-onnx 本地识别 → 意图判断 → 大模型生成 → TTS 播报。

语音识别使用的是开源模型 sherpa-onnx，完全离线运行，不依赖网络。针对控车场景，还准备了热词表（前进、后退、右转、九十度、记住这条路等 20 个词），显著提升了短指令的识别率。

大模型部分接入 DeepSeek，但**这里遇到了一个关键问题**：调用大模型接口本身并不联网，模型无法获知实时天气。最初的版本问"今天天气怎么样"，模型要么答不知道，要么编一个看似合理但完全错误的答案。

解决办法是**在提问前先把实时数据注入系统提示词**：调用 open-meteo 获取实况与三日预报（缓存 5 分钟），调用 ip-api 获取城市定位（缓存 1 小时），把结果拼进提示词，并要求模型"不知道的事就直说不知道，绝对不要编"。修复后同一个问题能准确回答"阴天，21 度，风 6 米每秒，降雨概率一成八"。

另一个改进是**回答长度分级**。最初所有问题都按 40 字以内回答，导致"讲讲平衡车为什么能站住"这种问题只能得到一句敷衍。现在按问题长度和关键词判断快答与讲解两档：日常问答限 40 字、响应 0.9 秒；讲解类放宽到 100～180 字并附带例子、响应 1.5 秒。

### 4.2 长期记忆

系统能把用户主动陈述的信息持久化到本地 JSON 文件，重启后依然记得。支持记录姓名、所在学校、正在做的项目等。实现上有两个细节值得说明：

- **区分陈述与疑问**。"我叫张三"是陈述，应当记住；"我叫什么"是疑问，绝不能把"什么"当成名字存进去。系统用疑问词表做过滤，并对姓名宾语做了非法字符检查。
- **触发词命中后走本地规则，不调用模型**。清除记忆这类操作如果经过大模型，既慢又可能被误解，现在直接匹配关键词执行，耗时 1 毫秒。

### 4.3 语音控车与示教再现

语音控车把自然语言转成动作。意图解析采用本地规则优先的策略：命中规则表直接执行，不联网、不等待；只有无法解析时才转交大模型做兜底理解。

**示教再现**是本项目最有特色的功能，用户说"记住这条路"开始记录，指挥车走一遍（前进、转向若干次），说"记好了"结束，之后说"走一遍"车就自动复现整条路径。路线以动作序列形式保存在本地，可以命名、可以有多个。

安全方面设置了三道约束：

| 措施 | 作用 |
|---|---|
| 动作白名单 | 大模型只能从 8 个动作里选一个，**不允许输出任何速度或 PWM 数值**，防止幻觉把车甩出去 |
| 指令自带时长 | 说"前进"默认只走 2 秒，"一直走"有 8 秒硬上限 |
| 跌倒锁 | 车身倾角超 ±50° 后锁死，语音指令无法将其重新拉起，必须人工按键复位 |

### 4.4 触摸屏控制中心

屏幕为 240×320 的 SPI 触摸屏，采用应用栈结构管理多个页面，主页以磁贴形式进入六个功能页：对话、天气、温湿度、遥控、语音控车、系统。

界面层刻意做到了"只负责看和判断哪里被点到"——所有数据由逻辑层填好后传入，因此**界面代码可以在电脑上直接渲染成图片**，不需要接硬件就能调试排版。这在开发中节省了大量反复烧录的时间。

系统页集成了 CPU 温度、负载、内存、磁盘、网络地址、运行时长、小车蓝牙状态，以及一个**风扇手动开关**（详见 4.5）。

### 4.5 CPU 温控风扇

树莓派 4B 在同时运行语音识别与界面渲染时温度会升至 45 ℃ 以上，因此加装了一路 PWM 调速风扇。驱动使用 TB6612，单片机侧则由树莓派 GPIO12 输出硬件 PWM。

控制策略为：40 ℃ 起转，70 ℃ 达到上限，中间线性调速，带 3 ℃ 迟滞避免频繁启停。启动采用**软启动**——6 秒内从 0 缓慢升到目标占空比，分 200 步，每步仅增加 0.35%。直接跳到 60% 会让电源看到方波式的电流冲击，软启动把这个冲击摊平。

运行中每秒读取电源管理芯片的欠压标志，一旦检测到欠压就自动降低占空比上限，是最坏情况下的自保护。

界面上还提供了手动开关：点击系统页第一行的"风扇"，可在「自动 → 手动开 → 手动关」之间循环，便于演示时强制启停。屏幕进程与风扇服务分属两个用户、不能直接争抢 GPIO，因此通过一组状态文件通信，实测切换响应 200～260 毫秒。

## 五、关键技术问题与解决

本节记录四个有代表性的问题。每个都遵循"现象 → 根因 → 验证 → 修复"的闭环。

### 5.1 车抽搐两下就停机

**现象**：语音下达"原地转一圈"，车抖动两下后停止，遥测显示航向角在 8 秒内暴涨 3410°。

**根因**：陀螺仪上电零偏标定没有静止检测。标定期间只要车被人碰过或放在不平处，就会把当时的角速度误认为零偏。若标定值偏差较大，航向积分会持续累加，车端闭环以为"已经转到位"而提前收手，用户看到的就是抽搐两下。

**修复**：标定改为 6 组 × 100 次采样，只有组内极差小于阈值（判定确实静止）才接受该组数据；同时主循环中增加角速度漂移低通滤波，漂移超限即置"陀螺仪异常"状态位，此时车端**直接拒绝转向指令**，上位机在界面上提示"陀螺仪没标好"，而不是让车带着错误的姿态数据乱转。

### 5.2 转圈一顿一顿

**现象**：转向过程不连续，车身走走停停。

**根因**：差速叠加时把差速量除以了 2（`平均PWM ± 差速/2`），导致转向力矩与平衡环的调节量处于同一量级，平衡环每次修正都会把转向"顶回去"一次，形成顿挫。

**修复**：转向期间差速量全量叠加，并设置最小差速下限防止低速时推不动；接近目标角度时按比例减速，避免过冲。修改后转向过程连续，实测 90° 用时 1.6 秒。

### 5.3 蓝牙断开了，界面还显示"已连接"

**现象**：车断电后，屏幕上的链路状态仍然是绿色的"已连接"，用户对着车喊半天没有反应。

**根因**：连接状态只在建立连接的那一刻写入一次，此后没有任何地方更新它。链路断开是一个"事件"，但界面读的是一个"变量"，事件发生了变量却没变。

**修复**：改为**用遥测数据的新鲜度判断链路死活**——车端每 50 毫秒发一帧遥测，超过 3 秒没有新数据即判定掉线，界面显示为暖色的"掉线"而非灰色的"未连接"（两者含义不同，前者表示曾经连上过）。掉线后 8 秒自动重连，无需人工干预。

这个问题带来一个通用经验：**状态显示必须绑定到"证据"，而不是绑定到"曾经发生过的事件"。**

### 5.4 风扇一跑树莓派就重启

**现象**：风扇启动瞬间树莓派重启，连续三次，并导致 SD 卡写入损坏（一个 Python 文件被写成全零字节）。

**根因**：原使用 2 A 电源，而树莓派 4B 空闲电流已有 0.6～0.8 A，风扇启动浪涌再叠加 0.6 A 以上，电压跌破 4.63 V 的欠压阈值，触发保护性重启。软启动只能摊平冲击，无法解决总量不足。

**修复**：换用官方 5.1 V / 3 A 电源。更换后实测：70% 与 100% 占空比各连续采样 220 次，欠压标志始终为 0，满速运行不掉压。

这里有一个排查技巧值得记录：`vcgencmd get_throttled` 返回值的**低 4 位表示"此刻"、高 4 位表示"曾经"**，而"曾经"的位只有**完全断电**才会清零，软重启不清。因此判断"是不是新电源造成的欠压"，必须先拔电再上电，看到 `0x0` 才是干净基线。

## 六、测试与结果

### 6.1 转向精度

测试条件：室内瓷砖地面，电池满电，每次转向后静止 1 秒再测下一个。

| 指令 | 实际转过 | 误差 | 用时 |
|---|---|---|---|
| 右转 90° | +91.0° | +1.0° | 1.6 s |
| 左转 90° | −84.0° | −6.0° | 3.4 s |
| 右转 45° | +42.0° | −3.0° | 1.4 s |
| 平均绝对误差 | — | **3.3°** | 平均 2.1 s |

误差来源已定位：陀螺仪零偏约 1.2 °/s，转向 2 秒即累积 2.4°。因此这 ±6° 中**大部分不是"转不准"，而是"测不准"**。改进方向是在线零偏跟踪（静止时把残余角速度缓慢学习为零偏），预计可压缩到 ±2°。

### 6.2 语音与对话响应

| 场景 | 响应内容 | 耗时 |
|---|---|---|
| 天气问答（含实况注入） | 阴天，21 度，风 6 米每秒，降雨概率一成八 | 1038 ms |
| 快答模式 | 28 字 | 860 ms |
| 讲解模式 | 142 字，含举例 | 1501 ms |
| 清除记忆（本地规则） | 直接执行，不经过模型 | 1 ms |

### 6.3 风扇与电源

| 测试 | 软启动 | 保持 | 采样次数 | 欠压次数 |
|---|---|---|---|---|
| 70% 占空比 | 6 s | 6 s | 220 | 0 |
| 100% 占空比 | 6 s | 6 s | 220 | 0 |

触摸屏切换风扇模式延迟实测 200～260 ms，界面约 0.7 秒内完成状态刷新。

## 七、不足与后续工作

项目仍存在明确的短板，后续按优先级排列如下：

1. **前进距离是开环的**。目前"前进两秒"按时间估算，地面打滑与电量变化都会影响实际距离。转向是闭环、前进不是，这是已知的不对称。要解决需用编码器里程做位置控制。
2. **命令词识别率与端到端延迟尚未系统测量**。目前只有定性观察（常用指令基本一次成功），缺少"每个词说 10 次记成功次数"这类定量数据。这是答辩前应补测的部分。
3. **转向误差仍受陀螺仪零偏限制**，如 6.1 所述，在线零偏跟踪尚未实现。
4. **视觉功能未接入**。摄像头已具备，计划实现视觉跟随与多模态指令（语音给意图、视觉给目标），这是投入产出比最高的扩展方向。

## 八、总结

本项目完成了从"能站住的平衡车"到"能听懂话的机器人"的改造，核心工作集中在三处：

- **架构上**，把转向闭环放在车端，使蓝牙延迟不再影响控制稳定性，这是整个系统能稳定运行的基础；
- **交互上**，把语音、触摸屏、对话助手整合到一台树莓派上，脱离了电脑依赖，开机即可独立工作；
- **工程上**，通过状态位、遥测新鲜度、欠压标志等"证据型"设计，让系统故障可观测、可定位，而不是只能靠猜。

技术上最有价值的收获不是某个功能跑通了，而是 5.1～5.4 这四个问题的排查过程：它们分别对应**标定不可信**、**控制量量级失配**、**状态显示脱离证据**、**供电余量不足**四类典型工程错误。这些问题在教科书上不会出现，只有在真实硬件上反复调试才会暴露。
